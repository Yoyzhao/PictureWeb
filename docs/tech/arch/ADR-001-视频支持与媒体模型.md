# ADR-001 视频支持与媒体模型

- **编号**：ADR-001
- **状态**：已接受（2026-10-25 方案落盘；同日按本决策实施完成，待验收）
- **关联**：`CHG-20261025-04`、M4 视频支持、`docs/plan/tasks/M4/STEP-视频支持.md`
- **决策日期**：2026-10-25

## 背景

PicGallery 当前只索引和浏览图片，文件夹中的视频被扫描器忽略。用户希望在本机与局域网内管理和浏览视频，不引入流媒体服务；客户端可能是 Windows、Android 或 iOS，且安装有 VLC 等本地播放器。用户同时要求不在客户端产生多余的播放缓存或视频副本。

现有收藏、标签、回收站、权限、书签、FTS 搜索与 keyset 分页全部围绕 `images` 表实现，这是本决策的主要约束。

## 决策

1. **统一媒体模型，扩展 `images` 表，不新建 `videos` 表**
   - 新增 `media_type`（`image`/`video`）、`duration`、`video_codec`、`audio_codec`；`format` 存容器，`width`/`height` 复用。
   - 存量数据经 `ALTER TABLE` 迁移后默认 `image`，不重写存量行。
   - `image_bookmarks` 增加 `media_filter`（`all`/`image`/`video`），并重建自动书签唯一索引，使书签恢复保持类型筛选。

2. **视频扫描与元数据**
   - 新增 `SCAN_VIDEO_EXTENSIONS`，与图片后缀分开配置；按扩展名判定 `media_type`。
   - 使用 `ffprobe -print_format json -show_format -show_streams` 读取时长、宽高、编码与容器；处理 90°/270° 旋转元数据。
   - 视频文件修改后更新元数据并删除旧封面，触发重新生成。

3. **封面生成**
   - 使用 FFmpeg 在视频 10% 位置（上限 10 秒）抽帧，再交给 Pillow 生成 `small`/`medium` WebP，沿用现有缩略图缓存与 `thumbnails` 表。
   - FFmpeg 子进程加超时与低并发信号量；失败时返回共享占位封面，不按视频逐份生成占位图。
   - 视频封面默认后台低并发预生成，可配置关闭；临时抽帧文件统一清理。

4. **直连播放，不引入流媒体服务**
   - 继续使用 Flask `send_file(conditional=True)` 提供 HTTP Range（实测返回 `206`、`Accept-Ranges: bytes`、`Content-Range`），支持浏览器和外部播放器拖动进度。
   - 不引入 HLS/DASH、不转码、不转封装；浏览器不支持的容器/编码交给本地播放器。
   - 视频响应使用 `Cache-Control: no-store`，避免浏览器把视频正文写入磁盘缓存；图片与封面仍使用现有缓存头。

5. **外部播放器联动按平台分支**
   - 桌面端：默认“复制播放地址”；可选下载 M3U 播放列表（小文件，用户主动触发）。
   - Android：使用 `intent://` 深链，`package=org.videolan.vlc`、`action=VIEW`、`type=video/*`，不产生文件。
   - iOS/iPadOS：使用 VideoLAN 文档化的 `vlc-x-callback://x-callback-url/stream?url=...`，只使用 `stream` 动作，不使用 `download`，避免视频写入设备。
   - `vlc://` 作为可选兜底（VLC iOS 2.3 起部分支持、2.4 起支持），不作为主路径。
   - 任何平台都保留“复制播放地址”兜底；非 Chromium 内核的 Android 浏览器、非 Safari 的 iOS 浏览器可能不支持深链。

6. **缓存与垃圾清理**
   - 服务端不生成视频副本，只缓存封面；临时抽帧文件在 `finally` 中删除，启动时清理遗留临时目录。
   - 删除、移动、重命名、文件夹移除、扫描对账沿用现有缩略图清理；新增定期 `prune_cache` 脚本清理无数据库引用的封面与回收站封面。
   - 客户端不自动下载视频；`<video>` 使用 `preload="metadata"`、不自动播放、不预加载下一段视频原文件；M3U Blob 使用后立即 `revokeObjectURL`。
   - 外部播放器自身的缓冲/缓存由其应用管理，本项目不承诺清理；本项目只保证不主动产生视频文件。

7. **权限边界**
   - 本轮不修改 `/raw`、`/thumbnail`、`/download` 的服务端权限校验，保持现有行为；媒体读取接口鉴权作为独立安全任务另行立项。
   - 若后续引入签名媒体 URL，M3U、深链与复制地址必须使用签名后的 URL。

## 后果

**正面**

- 复用现有收藏、标签、回收站、权限、书签、搜索、分页与多选逻辑，改动集中在媒体类型判定、封面与前端展示。
- 不转码、不复制视频，服务端磁盘与 CPU 成本可控；局域网直连即可播放和拖动。
- Android/iOS 使用深链时不产生文件；桌面端默认复制地址也不产生文件。

**负面与限制**

- 浏览器原生只支持部分容器/编码；MKV、AVI、WMV、FLV 通常不可播，HEVC 取决于平台；必须依赖本地播放器。
- iOS x-callback 与 Android intent 依赖 VLC 已安装且版本支持；Safari/Chrome 会要求用户确认，非主流浏览器可能降级为复制地址。
- 浏览器 `no-store` 会增加 Range 请求次数；对局域网影响可接受。
- 外部播放器自身的缓存无法由 Web 应用清理。
- `images` 表语义从“图片”扩展为“媒体”，文档与 UI 文案需同步为媒体中性表述。

**兼容性**

- 存量 `images` 行默认 `media_type='image'`，旧接口新增字段向后兼容。
- `image_bookmarks` 新增 `media_filter` 默认 `all`；旧书签恢复行为不变。
- 现有图片路径、收藏、标签、回收站与权限数据不需要迁移。

## 替代方案

| 方案 | 结论 | 原因 |
|------|------|------|
| 新建 `videos` 表与独立路由 | 拒绝 | 收藏、标签、回收站、权限、书签、搜索都要复制一套，维护成本和遗漏风险高 |
| HLS/DASH + 转码服务 | 拒绝 | 与本机/局域网场景不匹配，增加 CPU、磁盘与运维复杂度 |
| 移动端以 M3U 下载为主 | 拒绝 | Android/iOS 对下载文件的处理不一致，易残留且体验差 |
| 本地助手服务/浏览器扩展 | 不作为默认 | 需要每台客户端安装常驻程序，安全面与维护成本高；可作为后续增强 |
| 自定义协议 + 注册表脚本 | 不作为默认 | 每台客户端需注册，浏览器仍会弹确认；桌面保留 M3U/复制地址即可 |
