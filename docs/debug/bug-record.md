## [Bug-006] 视频封面预生成永久卡死，所有视频缩略图退化为占位图

- **ID**：Bug-006
- **日期**：2026-10-25
- **发生阶段/切片**：M4 视频支持（5D 后端 / 7 联调）
- **严重程度**：High
- **关联任务/变更**：T-030、T-034、CHG-20261025-04
- **影响范围**：所有视频封面（网格/书签/回收站）；后台缩略图预生成线程；后续新增文件夹的预生成
- **现象**：
  1. 用户新增 `F:\视频\4K` 后，10 个视频卡片全部显示深色占位图，接口返回 `image/jpeg` 且 `Cache-Control: no-cache, max-age=0`；
  2. 后端日志没有 `Thumbnail prebuild finished`、`Video poster prebuild finished`；
  3. 之后新增文件夹时日志提示 `Thumbnail prebuild already running; skipped folder 29`，预生成永久停止；
  4. 单独在另一个进程调用 `generate_thumbnail()` 可正常生成 WebP，说明 FFmpeg/文件本身没有问题。
- **复现步骤**：
  1. 扫描包含视频的文件夹，触发扫描后预生成；
  2. 请求任意视频 `/thumbnail?size=small`，返回占位图且 `cache` 为 `no-cache, max-age=0`；
  3. 再次新增/重扫文件夹，日志出现 `Thumbnail prebuild already running`；
  4. `py-spy dump` 该服务进程，可见 `thumb-prebuild-<id>` 线程阻塞在 `acquire_poster_slot`。
- **根因**：`server/app/services/video.py::acquire_poster_slot()` 只调用 `_poster_semaphore.acquire()`，**没有返回值**（Python 返回 `None`）；`thumbnail.py::_generate_video_thumbnail()` 用 `if not acquired` 判断是否拿到信号量。预生成路径 `background=True` 因此把“已获取”误判为“未获取”，直接返回共享占位图且不执行 `finally` 中的 `release_poster_slot()`：
  1. 第一个视频泄漏一个信号量占用；
  2. 第二个视频在 `acquire_poster_slot()` 上永久阻塞；
  3. 线程同时持有 `_prebuild_lock`，导致后续所有文件夹跳过预生成。
- **解决方式**：`acquire_poster_slot()` 获取成功后返回 `True`，使后台路径正确进入生成与 `finally` 释放；重启开发后端清空已泄漏的信号量状态。
- **修复产物/版本**：`server/app/services/video.py`（工作区，未提交 commit）
- **验证证据**：
  - `py-spy dump` 定位：`thumb-prebuild-27` 阻塞在 `acquire_poster_slot (video.py:348)`；
  - 修复重启后重扫文件夹 28：日志出现 `Thumbnail prebuild finished for folder 28: 10 images` 与 `Video poster prebuild finished for folder 28: 10 videos`；
  - 删除 32836、32842 的封面后重扫，两张 WebP 均重新生成；浏览器 HEAD 返回 `image/webp`、`public, max-age=86400`；
  - 该进程内后续缩略图请求不再排队，说明信号量无泄漏。
- **受影响阶段重验**：T-030 封面与缓存生命周期、T-034 联调；浏览器视频卡片封面恢复真实截图。
- **关联关系**：无（与 FLV 容器不可播是两件独立问题：后者是浏览器能力限制，不是缺陷）
- **状态**：已解决

## [Bug-005] 文件夹添加/扫描/移除存在索引冲突、并发与孤儿数据

- **ID**：Bug-005
- **日期**：2026-10-25
- **发生阶段/切片**：文件夹生命周期检查（5D 后端 / 5C 前端）
- **严重程度**：High
- **关联任务/变更**：T-027、CHG-20261025-03
- **影响范围**：`/api/folders` 添加、更新、删除、重扫；`/api/admin/folders/<id>` 解除关联；扫描器清理；侧边栏与管理页文件夹状态
- **现象**：
  1. 同一物理目录用不同大小写、分隔符或尾部分隔符添加时被当作不同文件夹；把父目录与子目录分别添加后，后添加的文件夹图片列表为空或与先添加的文件夹互相抢占。
  2. 文件夹刚添加处于 `pending` 时再次点击扫描仍会启动第二个扫描；服务重启后 `pending/scanning` 状态永久保留，重扫一直返回 409。
  3. 修改文件夹物理路径后不重扫，数据库继续保留旧路径图片；递归开关从开改为关后，子目录图片仍留在索引中。
  4. 删除文件夹后，该文件夹的手动/自动书签仍保留；管理员“解除关联”只删缩略图记录，不清缓存文件；硬删除没有根目录保护。
  5. 扫描清理只检查文件是否存在，删除图片时未清理收藏、标签、缩略图记录与缓存。
  6. 管理页增删文件夹后侧边栏不更新；添加失败时弹窗直接关闭并清空输入；当前文件夹被删除后图片页仍显示旧数据。
- **复现步骤**：
  1. 添加 `F:\_Pic\wallhaven`，再添加 `F:/_Pic/wallhaven/`，两者都被接受；
  2. 先添加父目录再添加其子目录，子目录扫描完成后图片数明显少于磁盘文件数；
  3. 添加文件夹后立刻调用 `/api/folders/<id>/scan`，可能同时存在两个扫描线程；
  4. 在扫描进行中删除文件夹，扫描线程仍可能继续插入图片；
  5. 解除关联后检查 `data/cache/small`，被删图片的缩略图文件仍在。
- **根因**：
  - 路径只做 `os.path.exists` 判断，没有 `normpath/normcase` 归一、绝对路径与目录校验，也没有父子路径重叠检测；`images.file_path` 全局唯一导致嵌套目录无法各自建立索引。
  - 重扫只拦截 `scanning`，检查与启动线程不是原子操作；扫描状态保存在数据库但线程在内存，重启后无人更新状态。
  - `PATCH path` 只更新 folders 表；扫描清理用 `os.path.exists` 判断，旧路径文件仍存在时不会删除旧索引。
  - 删除接口未处理 `image_bookmarks`；管理员解除关联未删除缓存文件；硬删除直接 `shutil.move`，未判断盘符根目录或应用数据目录。
  - 扫描清理直接 `DELETE FROM images`，未按外键依赖清理收藏、标签、缩略图（SQLite 未开启 `foreign_keys`）。
  - 前端管理页只刷新自己的文件夹表格，未同步 Pinia 文件夹 store；添加逻辑不判断请求失败。
- **解决方式**：
  - 路径统一 `expanduser + normpath`，以 `normcase` 比较重复并检测父子重叠，重复/嵌套返回 409；添加与 PATCH 校验绝对路径、存在性与目录类型，目录名自动提取兼容盘符根；
  - 重扫先用条件 `UPDATE ... WHERE scan_status NOT IN ('pending','scanning')` 原子抢占，再启动线程；`pending/scanning` 一律拒绝重复扫描、删除与路径修改；启动迁移把遗留的 `pending/scanning` 置为 `failed` 并写入中断提示；
  - PATCH 路径变更时重置扫描状态并自动重扫；扫描器记录本次遍历到的文件集合，按集合对账删除旧索引，并清理收藏、标签、缩略图记录与缓存文件；扫描过程中检测文件夹是否仍存在；
  - 抽取 `purge_folder_records` 供 `/api/folders` 与 `/api/admin/folders` 共用，统一删除图片、收藏、标签、缩略图记录与缓存文件、文件夹书签与权限；硬删除拒绝文件系统根目录及包含项目/数据库/缓存/回收站目录的路径，数据库失败时把物理目录移回原位；
  - 重扫权限收紧为管理员、文件夹所有者或拥有 `write` 权限的用户；
  - 前端添加失败保留弹窗与输入；管理页保存/删除后同步文件夹 store；`fetchFolders` 发现当前文件夹失效时回到“所有照片”；返回管理页后重新拉取图片。
- **修复产物/版本**：`server/app/routes/folder.py`、`server/app/routes/admin.py`、`server/app/services/scanner.py`、`server/app/services/thumbnail.py`、`server/app/utils/db.py`、`web/src/stores/folder.ts`、`web/src/stores/image.ts`、`web/src/components/Sidebar.vue`、`web/src/pages/AdminPage.vue`（工作区，未提交 commit）

## [Bug-004] 书签按钮无激活状态且再次点击无法取消

- **ID**：Bug-004
- **日期**：2026-10-25
- **发生阶段/切片**：M3 浏览位置书签（5C 前端 / 5D 接口）
- **严重程度**：High
- **关联任务/变更**：T-025、CHG-20261025-01
- **影响范围**：图片网格“记住这里”、灯箱“书签”按钮；书签创建接口
- **现象**：点击书签入口后提示“已保存当前位置”，但按钮没有任何激活状态；再次点击只会继续新建书签，无法取消已保存的位置。
- **复现步骤**：
  1. 登录后停留在图片网格，点击顶部“记住这里”；
  2. 提示保存成功，但按钮文字/样式不变；
  3. 再次点击，书签列表中新增一条重复位置，按钮仍无状态。
- **根因**：前端两个入口都固定调用一次性创建方法，没有把“当前图片/位置是否已有手动书签”绑定到按钮；`bookmarks` 也只在抽屉打开时加载，入口无法判断状态。后端创建接口未做同视图同锚点去重，重复点击会插入多条记录。
- **解决方式**：
  - 书签 store 新增 `bookmarkedImageIds`（手动书签锚点集合）、`findManualBookmark`（优先当前视图，否则取该图片最新一条）与 `toggleAt`：已存在则删除并提示“已取消书签”，不存在则创建；
  - 登录/恢复会话时立即拉取书签，创建成功后用接口返回值直接更新本地列表，保证按钮状态即时刷新；
  - 网格按钮增加 `is-active` 与“已书签/记住这里”文案切换，灯箱按钮增加 `active` 类与“书签/取消书签”标题；
  - `POST /api/bookmarks` 对同一用户、同一视图上下文、同一锚点去重，返回已有记录，避免双击产生重复。
- **修复产物/版本**：`web/src/stores/bookmark.ts`、`web/src/components/ImageGrid.vue`、`web/src/components/Lightbox.vue`、`server/app/routes/bookmarks.py`（工作区，未提交 commit）
- **验证证据**：
  - 网格：初始“记住这里” → 点击后“已书签”且带 `is-active` → 再次点击恢复“记住这里”并提示“已取消书签”；
  - 灯箱：标题“书签” → 点击后“取消书签”且带 `active` → 再次点击恢复“书签”；
  - 已存在书签的图片（31046）打开时，网格与灯箱均直接显示激活态；
  - `npm run check`、`npm run build`、后端 `py_compile` 通过；控制台无 error/warn。
- **受影响阶段重验**：5C/5D 书签功能通过；书签抽屉、锚点恢复未回归。

## [Bug-002] 灯箱移动真实图片总是报 Errno 13（开发后端沙箱启动）

- **ID**：Bug-002
- **日期**：2026-10-24
- **发生阶段/切片**：M2 性能与 UI 优化（灯箱交互增补，联调环境）
- **严重程度**：High
- **关联任务/变更**：T-024、CHG-20261024-10

- **现象**：灯箱内将 `F:\_Pic\wh` 中的图片移动到任何其他文件夹均返回 `moved=0`，错误为 `[Errno 13] Permission denied: '<目标路径>'`；关闭灯箱后直接调用同一移动接口仍失败。

  2. 接口返回 200，但 `moved=0`、`moved_ids=[]`，`errors` 含目标路径的 `Errno 13`；

- **解决方式**：停止沙箱后端，以非沙箱模式重启 `server/run.py`；应用代码不需要为 Errno 13 增加重试或绕过权限的逻辑。
- **修复产物/版本**：开发服务进程（5001）重启；无源码改动

- **受影响阶段重验**：灯箱/网格移动联调通过。
- **关联关系**：无
- **状态**：已解决（环境）

## [Bug-001] 灯箱收藏后瀑布流卡片收藏状态未同步

- **ID**：Bug-001
- **日期**：2026-10-24
- **发生阶段/切片**：M2 性能与 UI 优化（灯箱交互增补，5C 前端）
- **严重程度**：Medium
- **关联任务/变更**：T-024、CHG-20261024-10
- **影响范围**：灯箱与图片网格的收藏状态一致性；重命名后的卡片文件名同样受影响
- **现象**：在灯箱内点击收藏，灯箱按钮立即高亮；关闭灯箱返回瀑布流后，对应卡片的收藏图标仍为旧状态，刷新页面后才正确。
- **复现步骤**：
  1. 管理员登录开发环境，打开任意图片的灯箱；
  2. 点击工具栏“收藏”，灯箱按钮变为高亮；
  3. 关闭灯箱查看该图片卡片，卡片收藏图标未变化；
  4. 刷新页面后卡片状态才更新为已收藏。
- **根因**：`useImageStore.images` 为 `shallowRef`，`toggleFavorite` 替换数组元素后只调用 `triggerRef(images)`，未递增 `imagesVersion`。`VirtualWaterfall` 的 `layoutItems` 缓存的是元素对象引用，其更新依赖 `props.itemsVersion`；版本号不变时布局项仍指向替换前的旧对象，卡片继续渲染旧的 `is_favorite`。灯箱通过 `HomePage.currentImage` 读取 store，因此灯箱内状态正常，问题只在虚拟列表侧暴露。`renameImage` 采用同样的原地替换方式，存在同根因的卡片名称不更新问题。
- **解决方式**：在 `toggleFavorite` 与 `renameImage` 原地替换元素后递增 `imagesVersion`，保留 `triggerRef(images)`，使虚拟列表重新构建布局项引用并渲染最新对象。
- **修复产物/版本**：`web/src/stores/image.ts`（工作区，未提交 commit）
- **验证证据**：
  - 修复前（Chrome DevTools MCP）：灯箱收藏后 `lightboxFavActive=true`、`firstCardFavActive=false`；
  - 修复后：同一操作 `lightboxFavActive=true`、`firstCardFavActive=true`；再次点击取消收藏两者同步为 `false`；
  - `npm run check`、`npm run build` 通过；浏览器控制台无 error/warn。
- **受影响阶段重验**：5C 前端（灯箱/虚拟列表）通过；浏览器冒烟通过。
- **关联关系**：无
- **状态**：已解决
