## [Bug-010] 视频灯箱底部控制条遮挡视频原生进度条

- **ID**：Bug-010
- **日期**：2026-10-25
- **发生阶段/切片**：M4 视频支持（灯箱视频模式 UI）
- **严重程度**：Medium
- **关联任务/变更**：T-035；CHG-20261025-09
- **影响范围**：视频灯箱；开启底部“图片信息”时（默认开启）；桌面与移动端
- **现象**：视频播放时，底部自定义控制条与视频画面下沿重叠，遮住 `<video controls>` 原生进度条；续播提示也悬在视频底部，进一步压缩可视区域。
- **复现步骤**：
  1. 打开视频筛选并进入任意视频灯箱；
  2. 保持底部信息显示为默认开启；
  3. 观察视频底部原生进度条，被自定义控制条（含时间、倍速等）覆盖。
- **根因**：
  1. 视频垂直居中，`.lightbox.video-mode` 只预留固定 `--video-reserved: 120px`，底部实际可用空间不足；
  2. `.video-controls.with-meta` 因底部信息条存在而上移到 `bottom: 80px`，正好落在视频下沿的原生进度条位置；
  3. `.resume-chip` 独立悬浮在视频底部，未并入控制条。
- **解决方式**：
  1. 根节点增加 `meta-open` 状态类（`isVideo && showLightboxImageInfo`）；
  2. `--video-reserved` 改为按状态动态取值：桌面 180px / 320px（信息开启），移动端 200px / 340px；
  3. `.video-stage` 使用继承的 `--video-reserved` 计算宽度与 `aspect-ratio`，确保视频整体上移、底部留出原生进度条与控制条空间；
  4. 删除独立 `.resume-chip`，续播按钮并入底部控制条（`.vc-resume`），并与时间显示互斥。
- **修复产物/版本**：`web/src/components/Lightbox.vue`（工作区，未提交 commit、未部署）
- **验证证据**（Chrome DevTools 实测）：
  - 1280×900、信息开启：video bottom 743、controls top 765（间隙 22px），无重叠；信息条 829–873，controls bottom 823，间距 6px；
  - 1280×900、信息关闭：video bottom 812、controls top 821（间隙 9px）；
  - 503×847（移动端）：video bottom 565、controls 703–761、信息条 770–827，无横向溢出；
  - 续播按钮点击后播放位置由 0 跳至 33.9s 并开始播放；
  - `npm run check`、`npm run build` 通过。
- **受影响阶段重验**：M4 视频灯箱播放、视频信息显示、移动端布局。
- **关联关系**：与 Bug-006 同属视频灯箱体验问题
- **状态**：已部署（待用户启动验收）

## [Bug-009] 缩略图批量报 ERR_CACHE_READ_FAILURE，卡片显示空白

- **ID**：Bug-009
- **日期**：2026-10-25
- **发生阶段/切片**：M2/M4 媒体网格（客户端缓存）
- **严重程度**：Medium
- **关联任务/变更**：T-032；CHG-20261025-08
- **影响范围**：网格、回收站、书签抽屉中的缩略图 `<img>`；特定客户端 Chrome 缓存
- **现象**：浏览器控制台出现大量 `thumbnail?size=small:1 Failed to load resource: net::ERR_CACHE_READ_FAILURE`，对应卡片缩略图空白；服务端日志无 4xx/5xx，接口单独请求返回 200。
- **复现与排查**：
  1. 服务端抽查 3 个缩略图：均 200，`Content-Length` 与响应体一致，ETag/Last-Modified/Cache-Control 正常；
  2. 测试浏览器 24 个缩略图资源：`badCount=0`，缓存命中为 `transferSize=0` 且 `decodedBodySize>0`；
  3. 对同一批 10 个 URL 连续请求两次：0 失败；
  4. 客户端 C/D/F 磁盘剩余 73~954GB，排除磁盘满。
- **根因**：Chrome 本地 HTTP 磁盘缓存条目损坏，读取缓存时失败，请求未到达服务端；不是缩略图生成或接口错误。`Images loaded lazily and replaced with placeholders` 只是懒加载提示，不是错误。
- **解决方式**：
  1. 客户端硬刷新（Ctrl+Shift+R）或清除“缓存的图片和文件”；
  2. 应用层兜底：网格、回收站、书签抽屉的缩略图 `@error` 触发一次 `&retry=1` 重试，强制绕过损坏缓存条目走网络；每个 `图片 ID + size` 只重试一次，切换视图时清空重试状态。
- **修复产物/版本**：`web/src/components/ImageGrid.vue`、`web/src/pages/TrashPage.vue`、`web/src/components/BookmarksDrawer.vue`（工作区，未提交 commit）
- **验证证据**：
  - 对卡片派发 `error` 后 `src` 由 `thumbnail?size=small` 变为 `...&retry=1`，再次派发不再变化；
  - 重试 URL 请求返回 `200 image/webp`；
  - 服务端抽样与浏览器压力请求均无失败；
  - `npm run check`、`npm run build` 通过。
- **受影响阶段重验**：M2/M4 网格、回收站、书签抽屉缩略图加载。
- **关联关系**：与 Bug-007/Bug-008 同一轮反馈
- **状态**：已解决（客户端缓存 + 应用兜底）

### 时间线

- 2026-10-25 13:58：用户反馈大量 `ERR_CACHE_READ_FAILURE` 并询问缩略图是否加载不出来。
- 2026-10-25 14:02：服务端与浏览器压力测试确认接口正常，定位为 Chrome 磁盘缓存损坏。

## [Bug-008] 自动书签按视图上下文累积，出现多条“上次浏览”

- **ID**：Bug-008
- **日期**：2026-10-25
- **发生阶段/切片**：M3 浏览位置书签（5D 后端 / 5C 前端）
- **严重程度**：Medium
- **关联任务/变更**：T-025、CHG-20261025-08
- **影响范围**：`image_bookmarks` 自动书签、`/api/bookmarks/auto`、书签抽屉“继续浏览”
- **现象**：每次登录浏览后，“继续浏览”会出现新的“上次浏览位置”记录；开发库实际存在 4 条 auto 记录（`all`、`image`、`video`、文件夹 29+video），用户感知为每次浏览都会新增。
- **复现步骤**：
  1. 以不同筛选（全部/图片/视频）或不同文件夹浏览并触发自动进度；
  2. 打开书签抽屉，可见多条“上次浏览位置”；
  3. 查询 `image_bookmarks WHERE kind='auto'` 得到多条记录。
- **根因**：自动书签唯一索引与 upsert 条件按 `(user_id, folder_id, is_favorites, search_query, media_filter)` 区分，每种视图上下文各保留一条；前端 `lastAutoKey` 只在单次会话内去重，刷新后无法阻止新上下文插入。用户期望“全局仅保留最新一条自动进度，手动书签可多条”。
- **解决方式**：
  1. 迁移时按用户保留 `updated_at` 最新的一条 auto 记录，删除其余；
  2. 自动书签唯一索引改为 `(user_id) WHERE kind='auto'`；
  3. `save_auto_bookmark` 只按 `user_id + kind='auto'` 查找并更新全部视图字段（文件夹、收藏、搜索、媒体筛选、排序、锚点）；
  4. 手动书签逻辑不变，仍按视图+锚点去重，可保存多条。
- **修复产物/版本**：`server/app/utils/db.py`、`server/app/models/schema.sql`、`server/app/routes/bookmarks.py`（工作区，未提交 commit）
- **验证证据**：
  - 开发库迁移后 auto 记录由 4 条合并为 1 条，索引为 `idx_image_bookmarks_auto ON image_bookmarks(user_id) WHERE kind='auto'`；
  - 连续以 image/video 上下文调用 `/api/bookmarks/auto` 三次，返回同一 id（25），库内始终 1 条，上下文正确更新；
  - 恢复接口返回最新上下文；手动书签仍为 2 条；
  - 浏览器书签抽屉显示 1 条“上次浏览位置”+ 2 条手动书签。
- **受影响阶段重验**：M3 书签保存/恢复与抽屉展示；M4 媒体筛选上下文随单条自动进度更新。
- **关联关系**：与 Bug-007 同批次修复
- **状态**：已解决

## [Bug-006] 视频封面预生成永久卡死，所有视频缩略图退化为占位图

- **ID**：Bug-006
- **日期**：2026-10-25
- **发生阶段/切片**：M4 视频支持（5D 后端 / 7 联调）
- **严重程度**：High
- **关联任务/变更**：T-030、T-034、CHG-20261025-04
- **影响范围**：所有视频封面（网格/书签/回收站）；后台缩略图预生成线程；后续新增文件夹的预生成
- **现象**：
  1. 用户新增 `F:\视频\4K` 后，10 个视频卡片全部显示深色占位图，接口返回 `image/jpeg` 且 `Cache-Control: no-cache, max-age=0`；
  2. 后端日志没有 `Thumbnail prebuild finished`、`Video poster prebuild finished`；
  3. 之后新增文件夹时日志提示 `Thumbnail prebuild already running; skipped folder 29`，预生成永久停止；
  4. 单独在另一个进程调用 `generate_thumbnail()` 可正常生成 WebP，说明 FFmpeg/文件本身没有问题。
- **复现步骤**：
  1. 扫描包含视频的文件夹，触发扫描后预生成；
  2. 请求任意视频 `/thumbnail?size=small`，返回占位图且 `cache` 为 `no-cache, max-age=0`；
  3. 再次新增/重扫文件夹，日志出现 `Thumbnail prebuild already running`；
  4. `py-spy dump` 该服务进程，可见 `thumb-prebuild-<id>` 线程阻塞在 `acquire_poster_slot`。
- **根因**：`server/app/services/video.py::acquire_poster_slot()` 只调用 `_poster_semaphore.acquire()`，**没有返回值**（Python 返回 `None`）；`thumbnail.py::_generate_video_thumbnail()` 用 `if not acquired` 判断是否拿到信号量。预生成路径 `background=True` 因此把“已获取”误判为“未获取”，直接返回共享占位图且不执行 `finally` 中的 `release_poster_slot()`：
  1. 第一个视频泄漏一个信号量占用；
  2. 第二个视频在 `acquire_poster_slot()` 上永久阻塞；
  3. 线程同时持有 `_prebuild_lock`，导致后续所有文件夹跳过预生成。
- **解决方式**：`acquire_poster_slot()` 获取成功后返回 `True`，使后台路径正确进入生成与 `finally` 释放；重启开发后端清空已泄漏的信号量状态。
- **修复产物/版本**：`server/app/services/video.py`（工作区，未提交 commit）
- **验证证据**：
  - `py-spy dump` 定位：`thumb-prebuild-27` 阻塞在 `acquire_poster_slot (video.py:348)`；
  - 修复重启后重扫文件夹 28：日志出现 `Thumbnail prebuild finished for folder 28: 10 images` 与 `Video poster prebuild finished for folder 28: 10 videos`；
  - 删除 32836、32842 的封面后重扫，两张 WebP 均重新生成；浏览器 HEAD 返回 `image/webp`、`public, max-age=86400`；
  - 该进程内后续缩略图请求不再排队，说明信号量无泄漏。
- **受影响阶段重验**：T-030 封面与缓存生命周期、T-034 联调；浏览器视频卡片封面恢复真实截图。
- **关联关系**：无（与 FLV 容器不可播是两件独立问题：后者是浏览器能力限制，不是缺陷）
- **状态**：已解决

## [Bug-005] 文件夹添加/扫描/移除存在索引冲突、并发与孤儿数据

- **ID**：Bug-005
- **日期**：2026-10-25
- **发生阶段/切片**：文件夹生命周期检查（5D 后端 / 5C 前端）
- **严重程度**：High
- **关联任务/变更**：T-027、CHG-20261025-03
- **影响范围**：`/api/folders` 添加、更新、删除、重扫；`/api/admin/folders/<id>` 解除关联；扫描器清理；侧边栏与管理页文件夹状态
- **现象**：
  1. 同一物理目录用不同大小写、分隔符或尾部分隔符添加时被当作不同文件夹；把父目录与子目录分别添加后，后添加的文件夹图片列表为空或与先添加的文件夹互相抢占。
  2. 文件夹刚添加处于 `pending` 时再次点击扫描仍会启动第二个扫描；服务重启后 `pending/scanning` 状态永久保留，重扫一直返回 409。
  3. 修改文件夹物理路径后不重扫，数据库继续保留旧路径图片；递归开关从开改为关后，子目录图片仍留在索引中。
  4. 删除文件夹后，该文件夹的手动/自动书签仍保留；管理员“解除关联”只删缩略图记录，不清缓存文件；硬删除没有根目录保护。
  5. 扫描清理只检查文件是否存在，删除图片时未清理收藏、标签、缩略图记录与缓存。
  6. 管理页增删文件夹后侧边栏不更新；添加失败时弹窗直接关闭并清空输入；当前文件夹被删除后图片页仍显示旧数据。
- **复现步骤**：
  1. 添加 `F:\_Pic\wallhaven`，再添加 `F:/_Pic/wallhaven/`，两者都被接受；
  2. 先添加父目录再添加其子目录，子目录扫描完成后图片数明显少于磁盘文件数；
  3. 添加文件夹后立刻调用 `/api/folders/<id>/scan`，可能同时存在两个扫描线程；
  4. 在扫描进行中删除文件夹，扫描线程仍可能继续插入图片；
  5. 解除关联后检查 `data/cache/small`，被删图片的缩略图文件仍在。
- **根因**：
  - 路径只做 `os.path.exists` 判断，没有 `normpath/normcase` 归一、绝对路径与目录校验，也没有父子路径重叠检测；`images.file_path` 全局唯一导致嵌套目录无法各自建立索引。
  - 重扫只拦截 `scanning`，检查与启动线程不是原子操作；扫描状态保存在数据库但线程在内存，重启后无人更新状态。
  - `PATCH path` 只更新 folders 表；扫描清理用 `os.path.exists` 判断，旧路径文件仍存在时不会删除旧索引。
